# VoiceX 跨应用选中文本朗读（TTS）实施计划

> 文档状态：**v2.1 定稿（开发基线）**
> 更新日期：2026-08-12
> 修订说明：v2 由统筹人（Claude Code）整合 v1 主文与各专家意见（Grok、Trae 助手）重写；v2.1 依据外部审核意见（2026-08-12）修订六处 P1 接口矛盾并吸收全部 P2/P3 建议。v1 主文内容已整合进本文；各专家署名意见原文保留于附录 A；统筹人自有意见清单见 §2.4。本文档应在开工前以独立提交纳入 Git 作为基线（见 §7）。

## 1. 目标与范围

为 VoiceX 增加跨应用朗读能力：用户在任意应用中选中文字，按下可配置的全局快捷键，VoiceX 读取所选文字并通过所选 TTS 引擎朗读。

**形态结论（已定）**：在现有 VoiceX 中扩展，不做独立应用；代码上实现为边界清晰的独立 TTS 子系统（选区读取、TTS 后端、会话控制解耦）。macOS 首发，核心接口保持平台无关，Windows 后置。

**首版包含**：独立朗读快捷键；AX 选区读取 + 可关闭的 Copy 兼容模式；macOS 系统语音（默认、零配置）；一个云端 TTS 后端；语速/音量/引擎选择；开始、停止、取消与明确错误提示；不保存选区历史。

**首版不包含**：OCR、跨应用逐词高亮、暂停/继续、输出设备选择与 ducking、多云端供应商、Windows、扫描 PDF / Canvas / 远程桌面识别。

**非保证场景**（对外表述与文本注入能力对齐，不单独给出更乐观的承诺）：图片、扫描 PDF、Canvas、自绘控件、远程桌面、受保护内容、安全输入框。

### 2.1 路线级争议裁决

| # | 争议点 | 裁决 | 关键理由 |
|---|---|---|---|
| 1 | 独立应用 vs 扩展 VoiceX（附录 A §14.1） | **扩展 VoiceX** | 权限、热键、托盘、供应商配置、打包发布全部现成；两个应用分别索要辅助功能权限是体验倒退。§14.1 所列拆分条件出现时再评估，且先抽共享核心库 |

## 3. 技术方案

### 3.1 选区读取：分层策略

标准做法确认存在（AX API 为公开首选路径，Copy 模拟为业界事实兜底，PopClip/Bob/Easydict 均如此），但无单一 API 能覆盖所有应用。运行时顺序：

1. **AX 直接读取**：快捷键触发瞬间冻结前台应用与聚焦元素快照 → 读 `kAXFocusedUIElementAttribute` → `kAXSelectedTextAttribute`。成功时零副作用。
2. **AX 范围读取**：元素只提供选区范围时，经 `kAXSelectedTextRangeAttribute` + 参数化属性取文本。仅在类型与范围明确有效时执行，不吞 API 错误。
3. **Copy 兼容模式**（可关闭）：备份剪贴板（多类型，失败关闭规则见 §3.4）→ 模拟 Cmd-C → 以 `NSPasteboard changeCount` 判定复制是否发生（超时 300 ms）→ 读纯文本 → 无并发修改时恢复。以 `org.nspasteboard.TransientType` 标记，减少剪贴板管理器污染。
4. **明确失败**：HUD 区分"没有选中文字 / 当前控件不支持 / 权限缺失 / 复制超时 / 安全输入拒绝"，日志记录结构化失败类型（不记全文）。

**Electron/Chromium 兼容适配器**（按外部审核 #7 修订）：不对 Chrome/Electron 一概写入 `AXManualAccessibility`。实现为应用特定适配器：先查询目标进程是否支持该属性；仅对已验证的 Electron 应用（P0 名单中的 VS Code 等，逐个验证后加入适配表）启用，并记录是否改变了目标应用状态；Chrome 先测默认 AX 行为，必要时再评估按需启用方案。

```text
全局快捷键（单监听器内的 ReadSelection 动作）
  -> 冻结前台应用与焦点快照（HUD 不夺焦点）
  -> AX 直接读取 -> AX 范围读取 -> Copy 兼容读取
  -> 文本规范化（表格文本、换行、空白）
  -> 敏感度判定（Safe / Secure / Unknown，见 §3.4）
  -> TtsSession -> TtsBackend（系统语音直接朗读 | 云端合成+播放）
  -> HUD 状态
```

### 3.2 Rust 与 macOS 原生接口（技术路径可行；细节按阶段原型确认）

代码库已跨过三类桥的先例，无需 Swift/ObjC 混编；但以下依赖与格式细节需在对应阶段落地确认（外部审核 #10）：

- **C FFI**（AX API）：`permissions.rs` 已有 `AXIsProcessTrusted` 先例；取词只需约 5 个 ApplicationServices C 函数。注意 `core-foundation` 目前是传递依赖，需加为直接依赖以管理 CFString/CFTypeRef。
- **CGEvent**（模拟 Cmd-C）：`injector/clipboard.rs` 的 Cmd-V 实现已覆盖最深的坑（事件 source、flag 处理）；改键码即可，但**代码独立实现**（Grok §13.2）。
- **objc2**（NSPasteboard changeCount）：objc2-app-kit 已在依赖中，需加 `NSPasteboard` feature；`arboard` 不暴露 changeCount，故此处直调。
- **AVSpeechSynthesizer**（系统语音）：需新增 `objc2-avf-audio` 依赖。阶段 0 仅 speak/stop + isSpeaking 轮询（带启动锁存与启动超时）；阶段 3 实现 delegate（objc2 `define_class!`），API 生命周期与内存管理届时按 objc2 官方模式实现并单测。
- **云端音频播放**：reqwest + rodio（需新增依赖），纯 Rust 路径。云端流式响应的实际格式（PCM / WAV / MP3 / Base64 chunk）决定能否渐进播放，**在阶段 4 原型确认后再定播放方案**，不提前承诺。
- **线程约束**：AppKit 对象经 `MainThreadMarker` 在主线程访问（Tauri `run_on_main_thread` 调度）；AX 调用固定单线程串行。

### 3.3 架构组件

- **HotkeyManager 多动作路由**：一个系统级监听器（现有 `rdev::grab`），动作映射（`Dictate` / `ReadSelection`），设置时冲突检测，事件先解析为动作再路由到对应 Session。保留听写的轻点/长按/双击语义；TTS 首版单击语义：空闲=朗读、合成中=取消、播放中=停止；Escape 仅在 TTS 活动时生效。**任何阶段都不创建第二个全局键盘 hook**（外部审核 #2）。
- **SelectionReader**（平台无关接口）：`read_selection(context) -> SelectionResult { text, source(AX/AXRange/ClipboardCopy), sensitivity(Safe/Secure/Unknown), app_info, timing, diagnostics }`。macOS 首期实现；核心逻辑不依赖 AX 类型。
- **TtsBackend**（统一控制接口，按外部审核 #3 重构；自阶段 0 存在最小形态）：

```text
TtsBackend
  list_voices()
  start(request, cancel_token)
  stop()
  status()
├── MacSystemBackend
│     AVSpeechSynthesizer 直接朗读；不产音频 bytes，不经 SpeechPlayback
└── CloudBackend（阶段 4 引入）
      CloudTtsProvider：合成，返回 stream/bytes（capabilities/list_voices/synthesize/cancel、
        最大文本长度、流式与 SSML 声明、标准化错误）
      SpeechPlayback：rodio 播放（开始/停止/完成/失败事件；与 History 录音回放完全分离）
```

  系统后端不被强迫生成音频 bytes；云端后端内部组合合成与播放。前端引擎/音色选项来自共享定义（沿用 ASR/LLM 模式）。
- **TtsSession** 状态机：`Idle -> ReadingSelection -> Synthesizing -> Playing -> Idle`（系统语音路径 Synthesizing 与 Playing 合并为朗读中），所有阶段可取消；新请求取消旧请求；**状态变迁写入结构化日志**（可测性设计，供 harness 断言）。
- **ASR/TTS 资源协调**：开始听写先停 TTS；录音中触发 TTS 则拒绝并 HUD 提示；TTS 不申请麦克风权限；播放失败必须释放资源。

### 3.4 隐私与安全边界（失败关闭合同，按外部审核 #6 冻结）

**选区敏感度三态**：

- `Safe`：AX 明确判定为普通文本控件 → 正常处理。
- `Secure`：安全输入框、密码框（`kAXSecureTextField` 等）→ **拒绝读取**，任何路径（含 Copy）不得返回内容。
- `Unknown`：AX 无法判定聚焦控件类型（含 Copy 降级取得文本但无 AX 信息的情况）→ 允许**本地系统语音**朗读；**禁止发送云端**，HUD 提示原因并建议本地引擎。

**剪贴板失败关闭规则**：

- Copy 降级前必须成功快照所有声明为可恢复的 item/type；**发现无法快照的类型**（私有 UTI、file promise、延迟提供数据、超大数据）时**默认拒绝 Copy 降级**并返回明确错误，而不是覆盖后尽力恢复。
- 恢复承诺限定于冻结的 fixture 类型集：纯文本、HTML、RTF、PNG 图片、文件 URL；不承诺任意剪贴板内容 100% 恢复。
- 有并发修改（changeCount 变化非本操作所致）时不覆盖新内容。

**数据留存**：

- 默认供应商为本地系统语音；选择云端时明确提示"选中文字将发送给该供应商"。
- 默认不保存选区全文与合成音频；普通日志只记长度、来源、敏感度、目标应用、错误码。
- 诊断模式记录文本须用户显式开启并提示风险。
- 取消后不得继续下载、播放或把旧结果带入下一次会话。

## 4. 自动化优先的开发与验证策略

验证工作从"人工执行测试矩阵"改为自动化金字塔，人工只保留物理上无法自动化的残余项。

### 4.1 验证金字塔

| 层级 | 内容 | 执行方式 |
|---|---|---|
| L1 单元测试 | TtsSession 状态机（取消、重复触发、错误态）；热键动作路由与冲突检测；剪贴板快照/恢复逻辑（含失败关闭分支）；文本规范化；敏感度判定；错误分类；云端请求构造与分段 | `cargo test`，CI 可跑 |
| L2 端到端选区验证（三层，见 §4.2） | 脚本驱动真实应用完成"注入文本 → 选中 → 触发读取 → 断言结果" | 本机一条命令，输出 JSON 报告 |
| L3 残余人工清单 | 见 §4.4，共 5 项，多为一次性 | 显式清单，逐项打勾 |

### 4.2 端到端选区验证：三层结构（按外部审核 #4 修订）

macOS TCC/辅助功能授权按**进程身份**计（`AXIsProcessTrusted` 检查的是当前进程），独立 CLI 通过不能证明签名安装的 VoiceX.app 通过。因此 L2 拆为三层：

- **L2a 探针 CLI**（开发诊断用，不作发布门禁）：`selection-probe` bin，执行一次完整分层读取，输出 JSON：前台 app / Bundle ID、聚焦元素 role/subrole/支持属性、各路径成败与耗时、文本长度与 hash（默认不含全文，`--include-text` 供 fixture 比对）、敏感度判定、剪贴板恢复状态、结构化错误。用于快速迭代 SelectionReader 算法。
- **L2b VoiceX 进程内诊断命令**（发布门禁数据来源）：签名安装的 VoiceX 进程暴露一个诊断触发方式（Tauri command / deep link / 开发者设置入口），以真实 TCC 身份执行同一 SelectionReader 并输出同构 JSON。此即 Grok §13.1 常驻诊断能力的正式形态。
- **L2c 链路级 E2E**（发布门禁数据来源）：harness 经 CGEvent 注入真实朗读快捷键，触发 VoiceX 完整链路，断言 TtsSession 结构化日志的状态序列（Reading→朗读中→Idle）、取消行为与 HUD 不夺焦点。

**harness 公共设施**：

- **驱动脚本**：`scripts/tts/` 下每个 P0 应用一个独立 driver（AppleScript/JXA + System Events 或 CGEvent）：启动应用 → 载入 fixture 文本 → 程序化选中（Cmd-A / Shift+方向键 / 模拟鼠标拖选）→ **断言目标应用仍在前台**（否则该用例判 `invalid`，不计 pass/fail）→ 触发 L2b/L2c → 与 fixture 期望值比对。
- **fixtures**：中文、英文、中英混合、多行、标点/数字/URL/emoji、超长文本；负例：无选区、密码框（自建测试窗体）、焦点在 VoiceX 自身、剪贴板含不可快照类型。
- **报告**：汇总 JSON；`scripts/tts/evaluate_gate.py` 按 §4.3 输出 `GO` / `HOLD` / `INCOMPLETE` 及逐应用明细。
- **运行环境**：本机运行（需一次性授予终端与 VoiceX 权限）；CI 只跑 L1。

### 4.3 验收门槛（脚本判定；skip 规则按外部审核 #5 冻结）

**执行完整性规则**：

- P0 应用未安装或 driver 失效 → 门禁输出 `INCOMPLETE/HOLD`，**不得输出 GO**。
- P1/可选应用可 skip，不进入通过率分母。
- 报告必须输出：必测场景数、实际执行数、skip 数、invalid 数、成功率、每个 P0 应用的普通文本基线结果。

**`GO` 条件（数据来源为 L2b + L2c，L2a 不算数）**：

- P0 应用全部实际执行；每个 P0 至少一个普通文本基线场景通过；总场景通过率 ≥ 90%。
- 冻结类型集内剪贴板恢复率 100%（无并发修改时）；并发修改用例不覆盖新内容；不可快照类型用例正确拒绝降级。
- `Secure` 负例泄露数为 0；`Unknown` 来源发送云端计数为 0。
- Copy 路径 ≤ 300 ms 或明确超时错误；AX 路径 P95 ≤ 100 ms。
- 空选区、焦点在自身、无前台应用三负例返回各自明确错误类型。

未达门槛时先分类失败原因，不得以 OCR、静默剪贴板读取或防御性 fallback 掩盖（`HOLD` 路径）。

### 4.4 残余人工清单

1. **一次性系统权限授予**：终端与 VoiceX 的辅助功能 / 输入监控 / 自动化权限（macOS 强制人工）。
2. **默认值决策表确认**（§4.5）：不提出异议即视为按默认值执行。
3. **主观音质与延迟验收**：系统语音与云端各听一次（约 10 分钟，阶段 3/4 各一次）。
4. **不可脚本化应用抽查**（可选，非门禁）：微信、Word 等各做一次人工选中朗读。
5. **听写功能回归 smoke**：热键路由改造合入后人工听写一次（阶段 2，约 2 分钟；其余回归由 L1 路由测试覆盖）。

## 5. 实施阶段

每阶段列出任务、**自动化验收**（脚本/测试判定）与**人工参与**（对应 §4.4 编号）。按"原型优先"顺序执行：阶段 0 先跑通端到端，阶段 1–3 在原型基础上工业化，阶段 4 再接云端。

### 阶段 0：最小端到端原型（系统语音）

目标：最短路径跑通"热键 → 取词 → Mac 系统语音朗读 → 停止"，验证整条链路成立。

任务：
- **热键**：在现有 `HotkeyManager` 的同一 `rdev` 监听器内硬编码第二个动作绑定（⌥⌘R → `ReadSelection`）；暂缓通用配置与冲突检测；**不创建第二个全局 hook**。再按一次即停止。
- `selection` 模块最小实现：AX 直接读取 + Copy 兜底（含 `Secure` 拒读；先不做范围读取与完整错误分类，但快照失败即拒绝降级的规则从第一天生效）。
- `TtsBackend` trait 最小定义 + `MacSystemBackend` 实现：speak / stop；isSpeaking 轮询，带**启动锁存 + 启动超时**（避免启动竞态误判结束）。
- 无设置 UI、无云端、无 HUD 状态细分；关键事件打结构化日志。

自动化验收：smoke 脚本（CGEvent 注入热键 → 断言日志出现"取词成功 + 开始朗读 + 停止"序列）在 TextEdit 与 Safari 两个应用上通过。
人工参与：#1（一次性权限授予）；自行试用确认体验方向（非门禁）。

产出约定：原型代码按 §3.3 模块边界书写，后续阶段演进而非丢弃。

### 阶段 1：测试基建与选区读取验证

任务：
- `selection` 模块补全：AX 范围读取、多类型剪贴板快照/恢复（含失败关闭分支）、Electron 兼容适配器、前台快照冻结、文本规范化、敏感度三态判定、结构化错误分类。
- L2a 探针 CLI；**L2b VoiceX 进程内诊断命令**（同一 SelectionReader、真实 TCC 身份、同构 JSON 输出）。
- `scripts/tts/` harness：P0 应用 driver（含前台断言与 invalid 判定）、fixtures（含负例）、汇总报告、门禁脚本（`GO/HOLD/INCOMPLETE` 三态）。
- L1 单测：剪贴板快照/恢复边界、changeCount 判定、超时、失败关闭分支、规范化、敏感度判定、错误分类。

自动化验收：`cargo test` 全绿；基于 L2b/L2c 数据的 harness 报告过 §4.3 全部门槛，门禁脚本输出 `GO`。
人工参与：#1、#2（默认值确认）、#4（可选抽查）。

停止条件：`HOLD/INCOMPLETE` 时按失败分类处理选区问题，不进入阶段 4/5 的云端与发布工作（阶段 2 的热键重构不受阻塞）。

### 阶段 2：热键多动作路由工业化

任务：动作映射与冲突检测正式化（原型的硬编码绑定演进为可配置）；TTS 快捷键设置与持久化；快捷键录制流程适配；底层监听与 ASR Session 解耦。

### 阶段 3：系统语音链路工业化

任务：将原型演进为正式实现——TtsSession 状态机（结构化日志埋点）；**实现 `AVSpeechSynthesizerDelegate`（objc2 `define_class!`）替换轮询**，准确区分完成/停止/取消/失败；系统声音/语速/音量设置；HUD 读取/朗读/停止/错误状态；ASR/TTS 互斥策略落地。

## 6. 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| AX 覆盖率不足 | 常用应用读不到选区 | harness 先行度量；Copy 降级；按失败分类处理而非掩盖 |
| 探针与正式应用 TCC 身份不一致 | 门禁误判（CLI 通过 ≠ 应用通过） | 三层验证；`GO` 仅基于 VoiceX 进程内数据（L2b/L2c） |
| 剪贴板恢复不完整 | 破坏用户剪贴板 | 失败关闭：不可快照即拒绝降级；恢复承诺限定冻结类型集；changeCount 判定；并发修改不覆盖；TransientType 标记；可关闭兼容模式 |
| UI 自动化 driver 脆弱 | 应用升级导致 harness 误报 | driver 按应用隔离；前台断言 + invalid 判定；P0 失效 → `INCOMPLETE` 而非静默跳过 |
| CI 无法授予 AX 权限 | harness 不能上 CI | 分层设计：L1 上 CI，L2 本机一条命令运行 |
| 快捷键改造影响 ASR | 听写行为回归 | 单监听器多动作路由（自阶段 0）+ 路由单测 + 一次人工 smoke |
| TTS 与录音冲突 | 回声、资源争用 | 会话层互斥（听写优先），单测覆盖 |
| 云端首包延迟高 | 体验迟钝 | 系统语音为默认基线；云端分段 + 流式（格式确认后实施） |
| 敏感文本外发 | 隐私风险 | 本地默认、云端显式提示、不记全文、`Secure` 拒读、`Unknown` 不发云端（门禁强制） |
| AVSpeech delegate 样板与内存风险 | 实现出错 | 阶段 0 用轮询锁存过渡；阶段 3 按 objc2 官方模式集中实现并单测事件映射 |
| macOS 特有代码扩散 | Windows 成本增加 | SelectionReader/TtsBackend/Session 平台无关，AX 类型不出模块 |

## 13. Grok 补充意见

> 署名：Cursor Grok（2026-08-12）
> 约定：后续其他专家补充时，请另开带署名的章节，避免改写他人段落。

以下意见与上文主结论一致，只补充几处实现与产品上容易漏掉的点，不再重复"扩展现有应用 / 先验证选区 / AX 优先"等已有判断。

1. **探针最好做成可留存的诊断能力，而不是一次性抛掷代码。**
   选区读取探针可以挂在设置里的隐藏/开发者诊断入口（输出 Bundle ID、路径成败、耗时、失败类型），正式版也便于用户反馈"某某应用读不到"。这比写完即弃的 spike 更划算，也符合"失败要可见、不要静默吞掉"的仓库约定。

2. **现有剪贴板注入逻辑不要原样复用到取词。**
   [`src-tauri/src/injector/clipboard.rs`](../src-tauri/src/injector/clipboard.rs) 当前是"写入 → 粘贴 → 恢复"的注入方向；朗读取词是"备份 → 模拟复制 → 读纯文本 → 条件恢复"。备份类型、超时、`changeCount` 判定和并发修改策略都应单独实现并单测边界，避免把注入路径的假设带进读取路径。

3. **产品文案上要把"听写"和"朗读"并列讲清楚。**
   功能落地后，README / 设置页应明确 VoiceX 同时覆盖语音输入与选中朗读，避免用户仍按"纯听写工具"理解，或误以为系统"朗读所选内容"已被替代。默认快捷键不要占用系统常用的 Option-Esc。

4. **History 里的录音回放与 TTS 播放是两条线。**
   现有历史记录播放的是麦克风录音，不是合成语音。UI 与音频输出层都不要混用同一套"播放"语义，以免状态、资源释放和错误提示缠在一起。

5. **远程桌面类场景可直接继承既有预期。**
   VoiceX 在 RDP/特殊注入场景上已有脆弱性经验；选区读取在同类环境大概率同样偏弱。正式承诺和支持矩阵里应与注入能力对齐表述，而不是单独给出更乐观的覆盖率。

### 14.1 主张做成独立应用

理由：

- 听写与朗读方向相反，塞进同一产品会模糊定位；只想朗读的用户不应被引导去装带麦克风、ASR、听写状态机的应用。
- 独立应用可以只申请 Accessibility（取词）和音频输出，权限叙事更干净。
- 发布、定价、品牌和故障隔离都可以与听写解耦；听写回归也不会拖住朗读发版。

反驳（仍支持主文）：早期最大成本在选区读取与桌面壳，而不是供应商数量；两套热键/权限/打包的重复成本更高。若未来出现第 2.3 节中的产品条件，再拆不迟，且应先抽共享核心库。

### 14.2 主张 Copy 优先，而不是 AX 优先

理由：

- 实务上不少划词工具发现 AX 在浏览器/Electron/Office 上波动大，Command-C 反而更"够用"。
- 先做 Copy 可以更快做出纵向切片，用覆盖率换开发速度。

反驳（仍支持主文）：Copy 有剪贴板副作用和并发风险，不宜作为无提示的默认主路径；应以 AX 成功率为基线，Copy 作为可关闭的兼容模式，并在验证中单独度量其副作用是否可接受。

### 14.3 主张跳过专用探针，直接做系统 TTS 纵向切片

理由：

- 诊断探针本身不交付用户价值；不如用 `AVSpeechSynthesizer` 打通"热键 → 取词 → 朗读"，在真实使用中收集失败应用名单。
- 阶段划分过细会拉长"可感知进度"。

反驳（仍支持主文）：把供应商、快捷键重构和播放状态机与选区不确定性绑在一起，失败时难以判断卡在哪一层。最小探针可以很瘦（甚至无云、无完整设置页），但应先回答覆盖率与剪贴板安全，再投入多动作热键和 Provider 抽象。若团队强烈希望更快看到完整链路，折中做法是：**探针与系统 TTS 纵向切片做在同一分支，但验收仍分两道门**——先过选区门槛，再宣布功能可用。

## 15. Trae 助手补充意见

> 署名：Trae 助手（DeepSeek-V4-Flash）（2026-08-12）
> 约定：沿用第 13 节，另开署名章节，不改写他人段落；只补与上文不重复的点。

1. **阶段 5 选云端供应商前，建议补一份独立的 TTS 供应商调研简报。**
   项目里已有 `asr-provider-landscape` 的成熟做法可复用。选型维度建议定为：中文与中英混合自然度、首包延迟、是否支持流式与 SSML、成本与免费额度、取消/超时语义、Key 管理方式。首版只接一个，但"接哪个"应有数据支撑，而不是凭熟悉度或广告印象。

2. **热键触发瞬间必须冻结前台应用引用，朗读期间不要激活主窗口。**
   取词要用触发那一刻快照的前台应用 / AX 元素；一旦弹出 HUD 或主窗口抢焦点，取到的会变成 VoiceX 自己。现有录音流程已有"记录目标应用"的机制，朗读应沿用同一原则：**即时快照 + 不抢焦点**。

3. **补齐三种确定性行为：空选区、焦点在 VoiceX 自身、无前台应用。**
   空选区应给出区别于"当前控件不支持"的提示；焦点落在 VoiceX 自己（例如用户在设置页）时应明确不朗读并提示先切回目标应用。这些不能含糊，也不能静默吞掉。

4. **超长文本在首版就要有确定性行为，而不是拖到阶段 6。**
   建议首版就写死：超过供应商上限是"截断并提示"还是"按句/按段分段"。哪怕先只做"达到上限即提示、不合成"，也要明确，避免用户粘贴整篇文章时行为不确定。

5. **音频输出路由首版保持简单。**
   明确首版不做输出设备选择、不做 ducking（短暂压低其他音频）；默认输出设备即可。避免输出层过早复杂化，把设备/音量路由留到后续阶段。

6. **借机补一点自动化测试基线。**
   TTS 独立状态机和"一个监听器多动作路由"都值得补 `#[cfg(test)]` 单测（取消、重复触发、快捷键冲突检测），同时给 HUD / README 双语文案补词条。仓库目前没有成型的测试基线，TTS 是低成本建立状态机与路由测试的好切入点。

## 16. Trae 助手：相反观点与备选路径

> 署名：Trae 助手（DeepSeek-V4-Flash）（2026-08-12）
> 说明：本节收录与主文推荐路径相对的备选意见，便于多专家对照；不代表当前采纳结论。

### 16.1 主张首版纯系统语音、云端完全后置

理由：

- 云端即便只接一个，也要连带"多供应商抽象、Key 配置、连通性测试、取消/超时、流式/分段、隐私提示"一整条链路，会明显拖长首版。
- 对划词朗读，macOS 自带音色（含多语言）通常已"足够可用"；先把"热键 → AX 取词 → 系统语音朗读 → 停止/HUD"完整交付，云端放到验证之后作为独立次版。

反驳（仍支持主文）：

- 主文坚持"本地默认 + 一个云端"，核心是为了尽早验证 Provider 抽象与云端播放链路，避免架构空转；云端完全后置，阶段 5 的抽象会停留在纸面。
- 若团队目标是尽快拿到可用版本，可把"云端正交切片"作为**可选项**而非首版硬性范围，而不是彻底砍掉 Provider 抽象。
